새 관리 페이지의 기획과 디자인이 확정된 날, 제가 가장 먼저 하는 일은 API 명세를 type 파일로 옮기는 것입니다. 어떤 필드가 오고, 무엇이 nullable이고, 날짜가 어떤 형식인지를 Zod 스키마로 확정합니다. 그게 끝나면 Figma에서 URL을 복사합니다.

```
/figma-impl https://figma.com/design/****?node-id=****-****
```

이 명령을 입력하면 AI가 디자인을 읽고, 방금 작성한 type 파일을 명세 삼아, 우리 프로젝트의 표준 페이지 구조에 맞는 코드를 만들기 시작합니다. 테이블과 필터가 있는 목록 화면, 등록 모달, 수정 드로어까지요. 저는 결과를 검증하고 보완하는데, 뒤에서 다루겠지만 보완할 게 많지 않습니다.

처음 보면 모델이 좋아져서 되는 일처럼 보입니다. 그런데 같은 type 파일과 같은 URL을 아무 코드베이스에나 가져가면 재현되지 않아요. 이 결과를 만드는 건 대부분 AI가 아니라 코드베이스입니다. 이 글은 그 내용, 즉 **AI가 페이지 단위로 일할 수 있으려면 코드베이스에서 무엇이 미리 명확해야 하는지**의 기록입니다.

## 반대 방향에서도 해봤다

[하네스 2부작](/posts/agent-harness-for-legacy)에서 정리한 경험은 이 글과 방향이 반대였습니다. 가드레일이 없는 10만 줄 레거시에 AI를 들여야 했고, 코드를 고치기 전에 역할 분리·검토 게이트·측정으로 이뤄진 작업 구조(하네스)부터 설계해야 했어요. [실제로 돌려보니](/posts/agent-harness-refactor-measured) 효과를 만든 건 멀티에이전트 구조 자체가 아니라 측정과 안전 게이트, 사람 피드백을 강제한 규율이었고요.

그 작업에서 남은 결론이 하나 있습니다. **AI에게 맡길 수 있는 범위는 모델이 아니라 코드베이스의 상태가 정한다.** 레거시에서는 파일 하나를 고치는 데도 하네스가 필요했습니다. 참고할 기준이 페이지마다 달랐고, 어긋난 코드와 올바른 코드를 AI가 구분할 방법이 없었으니까요.

새 프로젝트를 시작하면서 이 질문을 반대 방향으로 적용해 볼 기회가 생겼습니다. 레거시에 AI를 들이는 게 아니라, **처음부터 AI가 짤 수 있게 코드베이스를 설계한다면 어디까지 맡길 수 있나.** 목표는 페이지 단위로 잡았습니다. 컴포넌트 하나, 함수 하나가 아니라 "이 관리 페이지를 만들어라"가 지시의 단위가 되는 것.

## 가설 — 보이는 것과 보이지 않는 것

프로젝트 `CLAUDE.md` 서두에 이 코드베이스의 설계 가설이 그대로 있습니다.

```md title="CLAUDE.md (발췌)"
**AI 보조 개발 프로세스**를 채택합니다.

Figma 디자인 ──→ AI가 코드로 전환 ──→ 개발자가 검증/보완 ──→ 완성

- AI가 잘하는 것: "보이는 것" — Figma UI, 코드 패턴, 프로젝트 구조
- AI가 못하는 것: "보이지 않는 것" — API 계약, 백엔드 스펙, 런타임 동작
```

AI는 보이는 것을 잘 다룹니다. Figma에 그려진 UI, 코드베이스에 이미 존재하는 패턴, 폴더 구조. 반면 보이지 않는 것은 코드 어디에도 없으니 추측하게 되고, AI의 추측은 그럴듯한 오류가 됩니다. 필드명을 지어내고, 있을 법한 엔드포인트를 만들어내는 식으로요.

이 구분을 받아들이면 설계 전략은 두 가지로 좁혀집니다.

첫째, **보이는 것의 범위를 표준화한다.** AI가 참고할 기준이 페이지마다 다르면 출력도 페이지마다 달라집니다. 기준이 하나로 통일돼 있으면 AI는 그 기준을 복제하는 일을 하게 되고, 그건 AI가 가장 잘하는 일입니다.

둘째, **보이지 않는 것은 추측할 여지를 없앤다.** 구조 안으로 감추거나, 사람에게 질문하게 강제하거나.

## 미리 만들어둔 세 레이어

페이지 하나를 위에서 아래로 자르면 디자인, 페이지 구조, 데이터 세 레이어가 나옵니다. 세 레이어를 각각 표준화했습니다.

### 첫째 레이어 — 디자인은 Figma에서 시작한다

표준화는 코드에서 시작하지 않았습니다. 디자이너와의 협의에서 시작했어요. 관리 화면에 쓰일 요소를 컴포넌트 단위로 정의해서 Figma 안에 디자인 시스템으로 먼저 만들었습니다. 같은 역할의 요소는 화면마다 새로 그리지 않고 같은 디자인 컴포넌트를 재사용하고, 색상과 타이포그래피는 토큰으로 정리하고, 각 요소에 속성값이 제대로 입력되도록요.

이게 중요한 이유는 AI가 Figma를 읽는 방식 때문입니다. MCP로 디자인 컨텍스트를 가져올 때, 잘 정의된 컴포넌트와 속성값은 구조화된 데이터로 읽힙니다. 반면 흩어진 사각형과 텍스트 뭉치는 좌표가 붙은 도형 목록일 뿐이에요. 같은 화면이라도 Figma가 어떻게 만들어져 있느냐에 따라 AI가 받는 입력의 품질이 달라집니다. **AI에게 "보이는 것"의 품질은 코드가 아니라 Figma에서 먼저 결정됩니다.** 디자인의 통일성을 높이는 협의는 그래서 사람을 위한 일이면서 동시에 AI 입력의 전처리이기도 했어요.

그 다음이 코드 쪽입니다. Figma의 디자인 시스템과 같은 모양의 컴포넌트 계층을 코드에 만들었습니다. 기본 UI 컴포넌트 24개 위에 디자인 시스템 컴포넌트 46개(2026년 9월 기준) — `FilterLayout`, `FormModal`, `FormDrawer`, `ListTable`, `DatePicker` 같은 것들이요. 색상은 hex 직접 사용을 금지하고 CSS 변수(디자인 토큰)만 쓰게 했고, border 같은 세부 표현도 토큰으로 정의했습니다.

### 왜 shadcn/ui였나

이 컴포넌트 계층의 기반으로 shadcn/ui를 골랐습니다. 이유는 배포 방식 하나로 요약됩니다. **설치가 아니라 복사라서요.**

MUI나 Ant Design 같은 완성형 라이브러리는 npm 의존성으로 들어옵니다. 컴포넌트 구현이 `node_modules` 안에 있으니, 우리 디자인을 적용하려면 라이브러리가 열어둔 테마 API와 스타일 재정의 지점을 통해야 해요. 흔한 수준의 조정은 그걸로 충분하지만, 시스템 전체를 우리 기준으로 다시 정의하려는 순간부터는 라이브러리가 정한 구조와 계속 충돌합니다. 재정의가 안 되는 내부 구조를 만나면 우회 코드가 쌓이고요.

shadcn/ui는 CLI가 컴포넌트 소스 자체를 저장소 안으로 복사합니다. 그 시점부터 그 파일은 라이브러리가 아니라 우리 코드예요. 원본 수정이 우회가 아니라 정당한 사용법입니다. 필요한 컴포넌트만 가져오니 라이브러리 전체를 의존성으로 받지 않아도 되고요. 실제로 우리 `button.tsx`가 어떻게 변했는지 보면 이 선택의 의미가 분명해집니다.

```tsx title="src/components/ui/button.tsx (발췌)"
const buttonVariants = cva("...", {
  variants: {
    theme: {
      // Primary Gradient (Figma: Theme=Gradient)
      gradient: "",
      // Primary Normal (Figma: Theme=Normal)
      normal: "",
      // Assistive (Figma: Theme=Assistive)
      assistive: "",
    },
    variant: {
      default: "",
      outline: "",
      // Legacy variants (shadcn/ui compatibility)
      destructive: "bg-destructive text-white inset-border-double ...",
      ghost: "hover:bg-accent hover:text-accent-foreground",
    },
    size: {
      // Figma Design System sizes
      lg: "px-4.5 py-3 gap-2 rounded-xl typo-body-1-semibold [&_svg]:size-6",
      md: "px-4 py-2.5 gap-1.5 rounded-[10px] typo-body-2-semibold [&_svg]:size-5",
      // ...
    },
  },
});
```

`theme` 항목은 shadcn 원본에 없습니다. 우리 Figma 디자인 시스템의 Theme 속성을 코드에 그대로 추가한 거예요. 주석이 Figma를 가리키고 있는 것(`Figma: Theme=Gradient`)이 이 계층의 성격을 보여줍니다. **Figma의 컴포넌트 속성과 코드의 props가 1:1이 되도록 원본을 고쳤고, 이건 코드를 소유하고 있어야 가능한 일입니다.** shadcn 원본의 variant는 하위 호환으로 남겨뒀고요.

Figma와 코드 양쪽이 같은 시스템을 공유하면 그 사이에 **매핑표**가 성립합니다. 실제로 스킬 문서에 이 표가 있어요.

```md title=".claude/skills/figma-impl.md (발췌)"
| Figma 디자인 요소  | 컴포넌트                                         |
| ------------------ | ------------------------------------------------ |
| 테이블             | `<DataTable>` / `<ListTable>`                    |
| 검색 + 필터 바     | `<FilterLayout>` + `<FilterSelect>` + ...        |
| 모달 폼            | `<FormModal>` + `<Section>` + Form 컴포넌트      |
| 사이드 패널/드로어 | `<FormDrawer>`                                   |
| 페이지 레이아웃    | `<TablePageLayout header={} filter={} table={}>` |
```

매핑표가 있다는 건 새 페이지의 UI 대부분이 새로 만드는 코드가 아니라 **기존 컴포넌트의 조합**이라는 뜻입니다. AI 입장에서 "이 디자인을 구현하라"는 요구가 "픽셀을 코드로 옮겨라"에서 "요소를 알아보고 매핑표에서 골라라"로 바뀝니다. 후자가 훨씬 덜 틀리는 일이고요.

### 둘째 레이어 — 컴포넌트 위의 패턴, 페이지 레이아웃

컴포넌트 단위가 디자인 시스템 기준으로 통일되고 나니, 그 위의 조합도 패턴으로 정리할 수 있었습니다. 관리 페이지는 어차피 헤더가 있고, 필터 영역이 있고, 테이블이 있어요. 이 반복을 `TablePageLayout`(header/filter/table 세 영역) 같은 공통 레이아웃과 `FilterLayout`, `FormModal`, `FormDrawer` 같은 래퍼 컴포넌트 — 공통 보일러플레이트를 내부에 포함하고 페이지는 내용만 채우게 하는 컴포넌트 — 로 패턴화하는 선작업을 했습니다. 그 결과 페이지 폴더는 매번 같은 구조로 구성됩니다.

```
src/pages/[feature]/
├── [feature].tsx        # TablePageLayout 조립
├── columns.tsx          # 테이블 컬럼 정의
├── api/                 # 팩토리 호출
├── type/                # Zod 스키마 + 타입 (도메인 명세)
├── store/               # createTablePageStore 팩토리
├── hooks/               # createCrudHooks 팩토리
└── components/          # Header / Filter / Table / CreateModal / UpdateDrawer
```

`CLAUDE.md`에는 "reference: `src/pages/station`을 기준으로 같은 방식으로 구현"이라는 규칙이 있습니다. 어느 페이지든 같은 위치에 같은 역할의 파일이 있으니, AI가 새 페이지를 만들 때 참고할 예제가 하나로 정해지고, 그 예제에서 벗어난 출력은 사람 리뷰에서 바로 눈에 띕니다.

### 셋째 레이어 — 데이터

[지난 글](/posts/factory-in-react)에서 다룬 CRUD 팩토리입니다. api 파일은 `createCrudApi` 호출 표현식 하나, hook 파일은 `createCrudHooks` 호출 하나로 끝나고, 쿼리 무효화·응답 검증·토스트 같은 절차는 전부 팩토리 안에 있습니다.

지난 글에서 이 구조의 효과를 "누가 작성하든 같은 코드가 나오게 만드는 것"이라고 했는데, **그 "누가"에는 AI도 포함됩니다.** AI가 쿼리 무효화 키를 틀리게 짜거나 검증을 빼먹는 일은 일어나지 않아요. 잘하고 못하고의 문제가 아니라, 페이지 쪽에는 그 코드가 아예 없기 때문입니다.

### 순서도 표준이다 — type 먼저, 없으면 mock

세 레이어의 표준이 정해지고 나니 개발의 순서도 표준이 됐습니다. **누가 페이지를 맡든 type 파일을 먼저 쓰고, 그 다음 AI에게 구현을 요청합니다.** 도입부에서 Figma보다 type 작성을 먼저 설명한 이유입니다.

백엔드 개발자가 페이지를 맡으면 보통 그 API를 본인이 만들었으니, 이미 아는 명세를 type 파일에 옮기는 것으로 시작합니다. 프론트엔드 개발자가 맡으면 API 명세 문서를 보고 type 파일부터 작성하고요. 출발점은 달라도 절차는 하나예요. 명세를 코드로 확정한 뒤에 구현을 시작한다. AI에게 페이지를 요청할 때 이미 type이 있으니, 보이지 않는 것 중 가장 큰 부분(API 명세)가 요청 시점에는 보이는 것으로 바뀌어 있습니다.

이 순서가 깨지는 경우가 하나 있습니다. 기획과 디자인은 확정됐는데 어떤 이유로 백엔드 API가 아직 없을 때요. 이때도 절차를 바꾸지 않고, mock api를 표준 인터페이스 그대로 만들어서 유지합니다.

```ts title="itemApi.ts (API 미구현 페이지, 일반화)"
import { MOCK_ITEM_DATA } from "./mockData";

// TODO: BE API 구현 완료 시 아래 mock 구현을 client.get으로 교체
export const itemApi = {
  getList: async (params: RequestItemList): Promise<ResponseItemList> => {
    await new Promise((resolve) => setTimeout(resolve, 500));

    const { offset = 0, limit = 15 } = params;
    const sliced = MOCK_ITEM_DATA.slice(offset, offset + limit);

    return responseItemListSchema.parse({
      items: sliced,
      total: MOCK_ITEM_DATA.length,
      offset,
      limit,
    });
  },
};
```

mock인데도 시그니처는 팩토리가 만드는 `getList`와 같고, 응답은 같은 Zod 스키마 검증을 통과합니다. 호출하는 쪽(hook, 컴포넌트)에서는 이 API가 mock인지 진짜인지 구분할 수 없어요. 나중에 백엔드가 준비되면 이 파일 하나만 팩토리 호출로 교체하면 끝입니다. AI 입장에서는 "API가 없는 페이지"라는 예외 케이스가 사라지고, 어느 페이지든 같은 절차가 성립합니다.

### 각 레이어로 결정의 개수를 줄이자

세 레이어를 통과하고 나면, 페이지 하나를 만들 때 AI가 실제로 결정하는 것은 얼마 남지 않습니다. 컬럼을 어떻게 구성하는지, 폼에 어떤 컴포넌트를 배치하는지 정도. 도메인 명세는 사람이 type 파일로 먼저 확정해서 넘겼고, 레이아웃도, 상태 관리도, 데이터 절차도, 색상도 이미 결정돼 있어요.

"AI에게 페이지를 맡긴다"는 말이 실제로 뜻하는 건 이것이라고 생각합니다. **AI의 능력을 늘리는 게 아니라 AI가 결정할 것을 줄이는 일.** 결정이 줄면 출력의 편차가 줄고, 편차가 줄면 검증이 빨라지고, 검증이 빨라져야 페이지 단위 위임이 실용이 됩니다. 페이지를 통째로 받아도 리뷰는 컴포넌트 하나를 확인하는 수준으로 끝나니까요.

## 공통 컴포넌트에 쓴 기법들 — 상태의 소유자를 정하는 일

세 레이어 중에서도 손이 가장 많이 간 건 공용 컴포넌트 레이어입니다. 이 컴포넌트들을 만들면서 render prop, 합성 컴포넌트(compound components), controlled/uncontrolled 같은 기법을 상황에 따라 골라 썼는데, 기준은 하나였어요. **이 상태의 소유자가 누구인가.** 공통 컴포넌트가 가져야 할 상태를 페이지로 넘기지 않고, 페이지가 정해야 할 것을 공통 컴포넌트가 대신 정하지 않는 것. 기법마다 실제 코드로 정리하겠습니다.

### render prop — 래퍼의 상태를 내용에 주입한다

`FormDrawer`는 수정/상세 드로어의 래퍼 컴포넌트입니다. 열림 제어, 조회↔수정 모드 전환, 저장·삭제 확인 다이얼로그, 변경 필드만 추려 전송하는 플로우까지 전부 래퍼가 처리하고, 페이지는 폼 내용만 채웁니다. 그런데 여기 문제가 하나 있습니다. 폼 필드가 활성화될지는 `isEditMode`에 달려 있는데, 그 상태는 래퍼 내부에 있어요.

```tsx title="FormDrawer.tsx (발췌)"
export interface FormDrawerProps<TFormValues extends FieldValues> {
  // ...
  /** 폼 컨텐츠 (render prop) */
  children: (props: {
    isEditMode: boolean;
    isLoading: boolean;
  }) => React.ReactNode;
}

// 래퍼가 상태를 소유하고
const [isEditMode, setIsEditMode] = React.useState(false);
// 내용을 렌더링할 때 주입한다
{children({ isEditMode, isLoading })}
```

`children`이 보통의 ReactNode였다면 페이지는 편집 모드를 알 방법이 없고, 그렇다고 `isEditMode`를 페이지로 끌어올리면 모드 전환 규칙(수정 중 닫기 시도 시 확인 다이얼로그 등)까지 페이지마다 다시 구현해야 합니다. children을 함수로 받으면 **상태 소유권은 래퍼에 남기면서 그 상태에 따른 표현만 페이지가 결정**할 수 있어요.

```tsx title="사용하는 쪽 (UpdateDrawer)"
<FormDrawer form={form} getDefaultValues={getDefaultValues} /* ... */>
  {({ isEditMode, isLoading }) => (
    <Section title="기본 정보" isLoading={isLoading}>
      <FormTextInput disabled={!isEditMode} /* ... */ />
    </Section>
  )}
</FormDrawer>
```

### 합성 컴포넌트 — 부모와 자식이 한 상태를 공유하는 선언형 API

추가 필터 영역(`AdditionalFilters`)은 "필터 추가" 버튼을 누르면 팝오버에서 필터를 골라 켜고 끄는 UI입니다. 어떤 필터가 선택 가능한지의 목록과, 켜진 필터만 렌더링하는 동작이 같은 상태(`visibleFilters`)를 봐야 해요. 이걸 `AdditionalFilters` 부모와 `AdditionalFilters.Select` / `AdditionalFilters.DateRange` 자식의 합성으로 풀었습니다.

```tsx title="AdditionalFilters.tsx (발췌)"
export const AdditionalFilters = Object.assign(
  forwardRef<AdditionalFiltersHandle, AdditionalFiltersProps>(
    function AdditionalFilters({ children }, ref) {
      const [visibleFilters, setVisibleFilters] = useState<string[]>([]);

      // children을 순회하며 label·paramKey를 추출해
      // "필터 추가" 팝오버의 목록을 자동으로 만든다
      React.Children.forEach(children, (child) => { /* ... */ });

      return (
        <AdditionalFiltersContext.Provider value={{ visibleFilters, /* ... */ }}>
          {children}
          {/* 필터 추가 팝오버 */}
        </AdditionalFiltersContext.Provider>
      );
    },
  ),
  { DateRange: AdditionalDateRange, Select: AdditionalSelect },
);
```

사용하는 쪽은 페이지에 필요한 필터를 JSX로 선언하기만 합니다. 팝오버 목록은 부모가 children에서 추출해 만들고, 각 자식은 Context에서 자기 표시 여부를 읽어 켜진 것만 렌더링해요.

```tsx title="사용하는 쪽 (Filter 컴포넌트)"
<AdditionalFilters ref={additionalFiltersRef}>
  <AdditionalFilters.DateRange label="수정일" startParamKey="from_updated_at" endParamKey="to_updated_at" />
  <AdditionalFilters.Select label="추가 분류" paramKey="category_filter" options={CATEGORY_OPTIONS} />
</AdditionalFilters>
```

설정 객체 배열(`filters={[...]}`)로 받는 API도 가능했지만 합성을 골랐습니다. 필터 구성은 페이지마다 다른 부분, 즉 페이지가 소유한 결정이라 페이지 코드에 선언으로 드러나는 게 맞고, JSX 선언이면 개별 필터에 페이지 전용 props를 추가하기도 자연스럽거든요. 부모가 관리하는 상태와 목록 추출은 사용처에서 아예 보이지 않고요.

### controlled — 값의 소유자가 컴포넌트 밖에 있을 때

필터 값을 다루는 컴포넌트들은 controlled입니다. `DateRangePicker`는 `value`/`onChange`로 값을 받아 그리기만 하고, `FilterSelect`는 Context를 통해 store의 값을 읽고 씁니다.

```tsx title="DateRangePicker.tsx (발췌)"
export interface DateRangePickerProps {
  /** 선택된 기간 */
  value?: DateRange;
  /** 기간 변경 콜백 */
  onChange?: (range: DateRange) => void;
}
```

이유는 필터 값의 소유자가 컴포넌트일 수 없기 때문입니다. 필터 값은 API 요청 파라미터가 되고, sessionStorage에 저장돼 <small>url로 상태를 관리해도 되지만 url에 노출하지 말아달라는 요구사항이 있었어요.</small> 페이지를 떠났다 와도 복원되고, 초기화 버튼 하나로 전부 리셋됩니다. 값이 컴포넌트 안에 있으면 이 세 요구를 하나도 만족할 수 없어요. 그래서 값은 전부 [테이블 페이지 store](/posts/factory-in-react)가 소유하고, 컴포넌트는 그리는 역할만 합니다.

### uncontrolled + 명령형 handle — 서버로 가지 않는 상태는 안에 둔다

반대로 `AdditionalFilters`의 `visibleFilters`(어떤 추가 필터가 화면에 펼쳐져 있는가)는 컴포넌트 내부 상태입니다. 이건 API로 전달되는 값이 아니라 순수한 화면 상태라, store에 올리면 서버와 무관한 값이 store에 섞여요. 그런데 딱 한 가지, 상위의 "초기화" 버튼이 눌리면 펼쳐진 필터도 접혀야 합니다. 이 동작 하나만 ref로 노출했습니다.

```tsx title="AdditionalFilters.tsx (발췌)"
export interface AdditionalFiltersHandle {
  reset: () => void;
}

useImperativeHandle(ref, () => ({
  reset() {
    setVisibleFilters([]);
    setDateRanges({});
  },
}));
```

```tsx title="사용하는 쪽 (FilterLayout에 연결)"
<FilterLayout onReset={() => additionalFiltersRef.current?.reset()} /* ... */>
```

전부 controlled로 만들면 모든 페이지가 `visibleFilters` 상태를 직접 관리해야 하고, 전부 uncontrolled로 두면 초기화가 안 됩니다. 기본은 내부 소유, 외부 개입이 필요한 동작만 명령형으로 노출 — 이 절충이 사용하는 쪽 코드를 가장 단순하게 만들었어요.

### 이 기법들이 페이지 단위 위임과 만나는 지점

네 기법의 공통점은 **복잡한 쪽이 공통 컴포넌트 안으로 들어가고, 사용하는 쪽에는 선언만 남는다**는 것입니다. 그리고 페이지 단위 위임에서 AI가 작성하는 건 정확히 그 "사용하는 쪽"이에요. AI는 `FormDrawer`의 모드 전환 규칙이나 `AdditionalFilters`의 children 순회를 알 필요 없이, 참조 페이지에 있는 선언 형태를 복제하면 됩니다. 컴포넌트 설계에서 상태 소유자를 정리해둔 것이, 결과적으로 AI가 결정할 것을 줄이는 일과 같은 일이었던 거죠.

## 표준을 AI에게 전달하는 두 가지 방법

표준을 만들어도 AI가 모르면 소용이 없습니다. 우리 프로젝트는 두 가지 문서로 전달합니다. 항상 적용되는 규칙은 `CLAUDE.md`로, 특정 작업의 절차는 스킬로.

### CLAUDE.md — 전역 규칙 168줄

`CLAUDE.md`는 AI가 이 저장소에서 일할 때 항상 읽는 문서입니다. 스택, 디렉토리 구조, 스타일링 규칙, 주의사항까지 168줄이에요. 쓰면서 지키려 한 원칙은 **규칙만이 아니라 결정의 이유를 함께 담는 것**입니다.

[React Compiler 글](/posts/react-compiler-bill)에서 정리한 메모이제이션 원칙이 좋은 예입니다. 측정으로 "새 코드에서 `useMemo`/`useCallback`을 기본적으로 쓰지 않는다, 참조 안정성이 필요한 곳은 이유를 주석으로 남기고 유지한다"는 원칙을 정했고, 그걸 그대로 `CLAUDE.md`에 넣었습니다. AI가 습관적으로 `useCallback`을 쓰는 걸 막는 게 목적이었는데, 넣고 보니 이 문서의 성격이 분명해졌어요. **사람 온보딩 문서와 AI 지침이 같은 문서가 됩니다.** 측정으로 정한 팀의 결정이 사람에게도 AI에게도 같은 기준으로 작동해요.

### 스킬 — 반복 작업의 절차서 608줄

반복되는 작업 네 가지는 스킬 문서로 분리했습니다. 합쳐서 608줄이에요.

| 스킬          | 용도                                      |
| ------------- | ----------------------------------------- |
| `/new-page`   | 새 페이지 전체 스캐폴딩 (15개 파일)       |
| `/add-api`    | CRUD API + React Query 훅 생성            |
| `/add-filter` | 필터 추가 (Type + Schema + UI 세 곳 동시) |
| `/figma-impl` | Figma 디자인 ➜ 코드 변환                  |

하네스 글에서 실행 단위는 서브에이전트, 참조 지식은 스킬이라고 구분했는데, 여기 넷은 전부 참조 지식입니다. 에이전트가 아니라 "이 작업은 이 순서로, 이 파일들을, 이 규칙으로"라는 절차서예요. `CLAUDE.md`에는 자연어 요청을 스킬로 매핑하는 표가 있어서, 사용자가 스킬 이름을 몰라도 "필터 추가해줘"라고 하면 `/add-filter`가 로드됩니다.

스킬에 절차를 담는 게 왜 중요한지는 `/add-filter`가 잘 보여줍니다. 필터 하나를 추가하려면 FilterState, request 스키마, Filter 컴포넌트 세 곳을 동시에 고쳐야 하는데, 한 곳이라도 빠지면 문제(<small>버튼이 죽는 다던가...</small>)가 됩니다. 스키마에서 빠진 필드는 `.parse()`가 조용히 지워버려서 API에 전달되지 않거든요. 스킬 문서에는 이 문제가 "흔한 실수" 목록으로 정리돼 있습니다. **사람이 이미 겪은 실수를 AI가 반복하지 않게 하는 장치**로, 코드로 강제할 수 없는 부분을 절차서로 보완하는 셈입니다.

### 보이지 않는 것은 질문하게 강제한다

앞에서 보이지 않는 것은 추측할 여지를 없앤다고 했는데, 팩토리로 감추고 type 먼저 순서로 좁히고도 남는 부분이 있습니다. 여기에 쓰는 장치가 질문 강제입니다. `/figma-impl`의 해당 부분 원문입니다.

```md title=".claude/skills/figma-impl.md (발췌)"
- Figma에 "보이는 것"만 코드로 변환 (UI, 레이아웃, 스타일)
- API 스펙, 필드명, 엔드포인트 등 "보이지 않는 것"은 추측하지 말고
  사용자에게 질문
```

`/new-page`에도 같은 규칙이 있습니다("확인이 안 되는 API 스펙은 추측하지 말고 질문할 것"). type을 먼저 쓰는 순서가 지켜지면 이 규칙이 발동할 일은 드뭅니다. 명세가 이미 코드로 있으니까요. 그래서 이건 평소를 위한 규칙이 아니라 예외 상황을 위한 규칙입니다. 명세가 아직 확정되지 않은 부분이 남아 있거나 type에 없는 값이 디자인에 등장하는 순간, AI가 그럴듯한 추측으로 채우는 대신 멈추고 사람에게 묻게 하는 것. 가설에서 세운 두 전략이 여기서 함께 적용됩니다. 보이는 것은 표준을 참조하게 하고, 보이지 않는 것은 사람에게 돌려보낸다.

이 외에 운영하면서 `CLAUDE.md`에 추가된 팁도 몇 개 있습니다. Figma URL에 `node-id`가 있어야 정확한 노드를 읽는다는 것, 기존 구현이 있으면 "수정/보완 방식으로"라고 명시해야 전체 재작성을 막는다는 것. 사소해 보여도 이런 문장 하나로 불필요한 전체 재작성을 막을 수 있습니다.

## 실제로 얼마나 효과가 있었나

[지난 글](/posts/factory-in-react) 마지막에 언급한 사례를 여기서 마저 설명하겠습니다. FE 경험이 없는 백엔드 개발자 한 명과 FE를 조금 다뤄본 백엔드 개발자 두 명이 각자 관리 페이지 하나씩을 맡았고, 세 명 모두 UI 구현까지 포함한 페이지 요구사항을 하루 안에 완성했습니다. <small>디자인 qa, 상용 배포까지는 시간이 조금 더 걸렸지만요...</small>

이 결과는 지난 글에서 다룬 데이터 계층 하나의 공이 아니라 이 글의 파이프라인 전체가 함께 만든 것입니다. 데이터 계층에서 사람이 쓰는 건 type 파일뿐인데 그건 백엔드 개발자가 이미 가장 잘 아는 API 명세였고(자기가 만든 API니까요), UI는 Figma와 매핑표를 따라 AI가 만들었고, 프로젝트 규칙은 `CLAUDE.md`가 AI에게 전달했습니다. FE 절차를 모르는 것이 페이지 완성의 장애물이 되지 않는 구조가 실제로 작동한 겁니다.

### 검증 단계에서 남는 일

파이프라인의 마지막이 "개발자가 검증/보완"인데, 표준이 완성된 뒤로는 이 단계에서 화면을 고치는 일이 많지 않습니다. 컴포넌트가 디자인 시스템 기준으로 이미 동일하게 구현돼 있으니, AI가 만든 화면은 대부분 그 컴포넌트의 조합이라 모양이 어긋날 여지가 별로 없어요. 실제로 보완하게 되는 건 문서 어디에도 없던 요구입니다. 예를 들어 폼 입력에서 방향키 조작을 막아야 한다는 세부 UX처럼, 디자이너·기획자의 머릿속에는 있었지만 Figma에도 명세에도 적히지 않아 전달되지 않은 것들. 이건 AI의 실패가 아니라 입력의 공백이라, 검증 단계에서 사람이 잡는 게 맞다고 생각합니다.

보완이 실제로 필요한 경우는 따로 있습니다. **기존에 구현한 적 없는 패턴의 페이지, 그리고 새로 생기는 공통 컴포넌트입니다.** 매핑표에 없는 요소가 디자인에 나오면 그 부분은 신규 구현이고, 신규 구현에는 표준이 적용되지 않으니 사람이 더 많이 확인해야 합니다. 다만 이때도 규칙이 있어요. `CLAUDE.md`의 "src/components/ 하위에 정의되어 있는 것을 먼저 사용", 그리고 `/figma-impl`의 "새 컴포넌트를 만들기 전에 기존 것으로 구현 가능한지 먼저 확인". AI는 기존 공용 컴포넌트로 조합을 먼저 시도하고, 정말 안 될 때만 새로 작성하게 돼 있습니다. 신규 구현을 막을 수는 없지만 남발은 막는 거죠.

### 표준은 계속 바뀐다 — 페이지 전용 컴포넌트를 공용으로 옮기기

그렇게 페이지 안에서 새로 만든 컴포넌트가 다른 페이지에서 다시 쓰이게 되면, 페이지 전용에서 공용 계층으로 옮기는 작업을 해주고 있습니다. 7월 중순 매출 집계 페이지를 작업할 때도 공용 컴포넌트 두 개(세그먼트 탭, 기간 선택 바)가 designSystem 레이어에 추가됐어요. 공용 컴포넌트가 1월 6개에서 시작해 7월 21개, 9월 현재 46개가 된 것도 이 순환의 결과입니다.

이게 표준화 작업의 실제 모습에 가깝다고 생각합니다. 표준은 한 번 세우고 끝나는 게 아니라, 페이지 작업이 표준을 넓히고 넓어진 표준이 다음 페이지를 빠르게 만드는 순환이에요. 그래서 매핑표는 페이지가 늘어날 때마다 항목이 추가되는 문서입니다.

## 반년 동안 표준이 유지됐나

데이터 계층을 팩토리로 교체한 3월 24일부터 이 글을 정리하는 9월 말까지 반년이 지났습니다. 표준을 만든 직후에 결과가 좋아 보이는 건 당연하니, 그 뒤로 페이지가 늘어나는 동안 표준이 실제로 유지됐는지 git으로 다시 확인했습니다.

| 시점                      | 페이지 폴더 | 공용 컴포넌트 | 표준 계층 | 페이지 코드 |
| ------------------------- | ----------- | ------------- | --------- | ----------- |
| 3월 말 (팩토리 교체 직후) | 8개         | 17개          | 10,200줄  | 7,841줄     |
| 7월 하순                  | 10개        | 21개          | 12,544줄  | 13,385줄    |
| 9월 말 (현재)             | 20개        | 46개          | 17,682줄  | 41,136줄    |

<small>공용 컴포넌트는 designSystem 폴더의 컴포넌트 수, 표준 계층은 공용 컴포넌트·기본 UI·레이아웃·상세 패널·팩토리·테이블 스토어의 줄 수 합계입니다.</small>

7월 중순부터 9월 초까지 새 페이지가 11개 추가됐습니다. 이 기간의 변화를 세 가지로 정리하면 이렇습니다.

**첫째, 새 페이지가 같은 구조로 나왔습니다.** 11개 중 9개가 station과 같은 폴더 구조(api / type / store / hooks / components)를 그대로 따랐습니다. 나머지 두 개는 구조를 벗어난 게 아니라 더 작아진 경우예요. 이용 집계 페이지는 매출 집계의 공용 컴포넌트를 그대로 쓰도록 만들어서 페이지 폴더가 36줄이고, 이용 내역 페이지도 충전 내역과 컴포넌트를 공유합니다. 팩토리 사용 여부도 [지난 글](/posts/factory-in-react)에서 정한 기준대로 나뉘었습니다. CRUD 모양인 7개는 전부 팩토리를 썼고, 집계·대시보드처럼 CRUD 모양이 아닌 4개는 쓰지 않았어요. 그리고 이 11개 페이지는 모두 표준을 설계한 제가 아니라 5월에 합류한 새 팀원이 작업했습니다. 백엔드 개발 경력으로 시작해 프론트엔드를 맡게 된 분이에요. 데이터 계층을 보면 이 조건이 왜 문제가 되지 않았는지 드러납니다. 이분이 만든 운영사 관리 페이지는 api 파일 22줄, hook 파일 34줄, type 파일 209줄이고, 충전 카드 페이지는 20줄, 33줄, 247줄입니다. [지난 글](/posts/factory-in-react)에서 잰 station의 구성(type 332 / api 21 / hook 38줄)과 비율이 같아요. 작성한 코드의 대부분이 type 파일, 즉 API 명세이고, 그건 백엔드 개발자에게 가장 익숙한 영역입니다. 쿼리 무효화나 응답 검증 같은 프론트엔드 절차는 팩토리가 처리하니 새로 배울 필요가 없었고, 화면은 station 참조 구조와 매핑표를 따라 만들어졌습니다. 앞에서 소개한 "백엔드 개발자 세 명이 하루 만에 페이지를 완성한" 사례가 한 번의 결과가 아니라, 두 달 동안 11개 페이지에서 반복 증명 된거죠. "누가 작성하든 같은 코드가 나오게 한다"는 목표가 작성자와 그 사람의 경력이 바뀐 상태에서도 유지됐어요.

**둘째, 팩토리와 규칙 문서는 거의 바뀌지 않았습니다.** 반년 동안 두 팩토리 파일을 고친 커밋은 8개이고, 대부분 모든 페이지에 한 번에 적용되는 정책 변경이었습니다. 예를 들어 "내보내기 파일명에 다운로드 시각 추가"는 `createCrudApi.ts` 한 파일만 고친 커밋인데, 팩토리를 쓰는 13개 페이지 전부에 적용됐어요. `CLAUDE.md`는 7월 하순 156줄에서 168줄로 늘었는데, 추가된 건 권한 규칙 문서 링크와 UI 문구의 따옴표 규칙이고, 스킬 문서는 7월 이후 한 번도 바뀌지 않았습니다.

**셋째, 페이지가 늘어난 만큼 표준도 넓어졌지만 훨씬 느리게 늘었습니다.** 7월 하순부터 두 달 동안 페이지 코드는 3.1배가 됐고, 표준 계층은 41% 늘었어요. 7월에 1:1에 가깝던 표준과 페이지의 비율이 지금은 1:2.3입니다. 늘어난 표준 코드의 상당수는 앞에서 설명한 옮기기 작업의 결과이고, 이 작업은 제가 맡았습니다. 새 팀원이 페이지를 만드는 동안 저는 두 페이지 이상에서 반복되는 부분을 찾아 공용 계층으로 옮겼어요. 역할이 이렇게 나뉘어 있었기 때문에 페이지가 빠르게 늘어나는 동안에도 공용 컴포넌트가 한 기준으로 관리됐습니다. 이 기간 커밋 기록을 보면 "소속 필터를 공용 컴포넌트로 승격", "달력 로직 3중 복제를 공용 모듈로 통합" 같은 작업이 여러 번 있었고, 상세 조회 패널용 공용 컴포넌트 묶음(detailPanel)도 이때 새로 만들어졌습니다. 표준 자체가 넓어진 경우도 있습니다. 8월에는 목록 페이지마다 반복되던 진입 코드(컬럼 설정, 딥링크 처리)를 `TablePage`라는 공통 셸로 옮겼는데, 이 커밋 하나로 13개 페이지 폴더가 함께 바뀌었고 전체 코드는 115줄 줄었어요.

반대로 표준 밖에 남은 코드도 있습니다. 페이지 폴더 중 두 개가 6,000줄을 넘는데, 이걸 표준이 실패한 곳보다는 다음에 공용으로 옮길 후보가 모인 곳 입니다. 충전기 페이지에는 원격 제어 모달, 커넥터 상태 이력, 충전 프로파일 편집처럼 장비를 다루는 화면이 들어 있고, 고객사 페이지는 한 폴더 안에 고객사 관리와 계약 관리 두 화면이 있으며 계약 등록이 여러 단계의 위저드로 진행됩니다. 둘 다 매핑표에 아직 없는 형태예요. 고객사 페이지의 위저드 모달, 카드 선택, 단가 입력 필드는 이미 designSystem으로 옮겼고, 요금제 페이지가 카드 선택을 같이 쓰고 있습니다. 나머지도 같은 형태의 화면이 다른 페이지에서 한 번 더 나오면 옮길 예정입니다. 앞에서 설명한 순환이 아직 끝나지 않은 부분인 거죠.

## 성립 조건과 한계

**표준 밖에서는 성립하지 않습니다.** 페이지 단위 위임은 정확히 "표준화된 범위" 안에서만 작동해요. 공통 컴포넌트로 만들어지지 않은 디자인, 특정 페이지에서만 쓰는 시각 표현이나 비즈니스 로직 패턴은 위에서 말한 대로 사람이 맡습니다. 공통 레이아웃과 래퍼가 담당하는 건 "관리 페이지의 공통 형태"까지고, 페이지의 고유한 부분은 언제나 남아요. 그리고 그게 맞다고 생각합니다. 고유한 부분까지 표준에 포함시키면 팩토리에 페이지별 분기가 쌓이는 것과 같은 문제가 공통 컴포넌트에서 반복될 테니까요.

**페이지 단위는 무검증이 아닙니다.** 파이프라인의 세 번째 단계가 "개발자가 검증/보완"이고, 보이지 않는 것 중 질문으로 해결되는 건 스펙 정도입니다. 런타임 동작 — 이 폼이 실제로 제출되는지, 필터 조합이 예상대로 동작하는지 — 은 여전히 사람이 확인합니다. 하네스 글의 결론이 여기서도 그대로예요. 속도는 자동화가 내고, 그 결과를 검증하고 멈출지 판단하는 건 사람이 한다.

**순서를 바꿀 수 없습니다.** 표준이 정해지기 전에 AI에게 페이지를 맡기면, 참고할 기준이 없으니 페이지마다 다른 코드가 나오고, 그 결과물이 다시 다음 페이지의 참고 기준이 되면서 편차가 누적됩니다. 지난 글에서 다룬 레거시처럼 같은 역할의 코드가 페이지마다 달라지는 문제가, 이번에는 **AI의 속도로 반복**되는 거죠. 표준화가 먼저고 위임이 나중입니다. 이 순서만큼은 도구가 좋아져도 바뀌지 않을 거라고 생각해요.

**측정의 한계도 정확히 말해두겠습니다.** "하루 안에 완성"은 기록이 아니라 증언이고, 대조군이 없으니 리드타임 개선을 숫자로 주장할 수 없습니다. 표준화 기간과 반년 운영의 git 실측도 통제된 비교가 아니에요. 줄 수와 폴더 구조는 코드가 같은 모양인지를 보여줄 뿐, 개발 속도를 직접 보여주지는 않습니다. 근거가 되는 실측 — 팩토리가 지운 반복, 페이지당 코드 구성 — 은 [지난 글](/posts/factory-in-react)에 있습니다.

**그리고 표준 자체도 한 번 정하면 끝이 아닙니다.** 충분히 일반적이라고 생각했던 공통 레이아웃과 래퍼가 도메인 요구를 감당하지 못해 여러 방식으로 나뉜 지점들도 존재합니다. 앞으로 새로운 표준으로 만들어가야하죠.

## 마무리

레거시에서는 AI를 들이기 위해 하네스라는 작업 구조를 따로 설계해야 했습니다. 새 프로젝트에서는 하네스를 따로 만드는 대신 코드베이스 자체가 그 역할을 하도록 설계했어요. 시작은 코드가 아니라 디자이너와의 Figma 표준화였고, 그 위에 shadcn을 복사해 소유한 컴포넌트 계층, 패턴화된 페이지 레이아웃, 절차를 감춘 데이터 계층, type을 먼저 쓰는 개발 순서까지 세 레이어의 표준을 만들었습니다. git으로 재보니 그 표준에 한때 페이지 전체와 맞먹는 12,500줄의 코드와 기능 개발보다 긴 시간이 들어가 있었고요. 표준은 `CLAUDE.md` 168줄과 스킬 608줄로 사람과 AI가 같은 기준을 읽게 했고, 보이지 않는 것은 추측 대신 질문하게 강제했습니다. 그 위에서 type 파일 하나와 Figma URL 하나로 시작하는 페이지 단위 위임이 성립했고, FE를 모르는 개발자 세 명이 하루 만에 페이지를 완성하는 데까지 왔습니다. 그리고 반년이 지나는 동안 페이지가 두 배로 늘고 작성자가 백엔드 출신의 새 팀원으로 바뀌어도, 새 페이지는 같은 구조로 나왔고 팩토리와 규칙 문서는 거의 바뀌지 않았습니다.

두 방향을 다 겪고 남은 결론은 하나입니다. **AI에게 얼마나 맡길 수 있는지는 모델이 아니라 코드베이스가 정한다.** 모델은 우리가 만들 수 있는 게 아니지만 코드베이스는 우리가 설계할 수 있고, 이 프로젝트에서 페이지 단위 위임이 된 것도 모델이 특별해서가 아니라 코드베이스를 그렇게 설계해뒀기 때문입니다. 페이지 단위 위임은 AI가 더 많이 결정하게 해서가 아니라 더 적게 결정하게 해서 성립했습니다. 그리고 결정을 줄이는 일 — 디자인의 통일, 표준화, 강제, 절차화 — 은 AI가 아니라 사람이 미리 해둬야 하는 일이고, 한 번 해두면 끝나는 일이 아니라 페이지마다 표준을 보완해 가는 일이에요.
