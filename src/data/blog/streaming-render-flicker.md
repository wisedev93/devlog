회사에서 AI Agent가 답하는 관제 화면의 웹 프론트엔드를 만들고 있습니다. 운영자가 자연어로 물으면 모델이 도구를 불러 데이터를 읽고, 답변 안에 차트·지도·표 블록을 섞어서 보내요. 답변은 SSE로 조각조각 도착합니다.

첫 구현은 단순했어요. 조각이 오면 텍스트에 붙이고, 상태를 바꾸고, 마크다운을 다시 그렸습니다. 돌려 보니 네 가지가 눈에 걸렸어요.

1. **긴 답변일수록 화면이 버거워했습니다.** 조각마다 마크다운 전체를 다시 파싱하니까요.
2. **자연스럽게 보이려고 말풍선에 페이드를 걸었더니, 이미 읽던 문장까지 같이 깜빡였습니다.**
3. **차트 블록이 오는 동안 빨간 "차트를 그릴 수 없습니다" 화면이 번쩍였다가 마지막에 차트로 바뀌었습니다.** JSON이 반만 온 상태로 차트 렌더러에 들어갔기 때문이에요.
4. **모델이 도구를 부르는 동안 글자가 멈추면, 답변이 끝난 것처럼 보였습니다.** 실제로는 아직 스트림이 열려 있었는데요.

이 글은 그 네가지를 하나씩 고친 기록입니다. 그리고 각 기법이 **언제 효과가 없는지**도 같이 적었어요. 네 번째까지 읽고 나면 "그냥 다 켜면 되는 것 아닌가"에 답이 될 겁니다.

> 본문의 비교는 [/labs/streaming-render](/labs/streaming-render)에서 직접 재생해볼 수 있어요. 같은 가짜 스트림을 두 말풍선에 동시에 흘리고, 기법을 하나씩 끄면서 렌더 횟수와 반쪽 차트가 실패 화면으로 보인 횟수를 셉니다.

## 1. 조각마다 그리지 않는다 — 50ms 코얼레싱

### 문제

SSE 조각은 몇 글자씩 옵니다. 조각마다 `setState`를 하면 조각 수만큼 렌더가 일어나고, 렌더마다 마크다운 전체를 다시 파싱해요. 답변이 길어질수록 파싱할 텍스트도 길어지니 비용이 계속 커집니다.

### 고친 방법

조각이 와도 바로 그리지 않고, 50ms 안에 온 조각을 모아 한 번에 그립니다. 대신 **확정 시점**은 기다리지 않아요. 첫 글자, 스트림 종료, 출처나 도구 정보가 도착한 순간은 바로 그립니다.

```ts
let flushTimer: ReturnType<typeof setTimeout> | null = null;

const schedulePaint = () => {
  if (flushTimer == null) flushTimer = setTimeout(paint, 50);
};

for await (const frame of stream) {
  const prev = run;
  run = reduce(run, frame);

  const settled =
    run.sources !== prev.sources ||
    run.toolCalls !== prev.toolCalls ||
    run.status !== prev.status;

  if (!hasBubble || settled) {
    clearTimer();
    paint(); // 첫 글자와 확정 시점은 바로
  } else if (run.text !== prev.text) {
    schedulePaint(); // 나머지는 50ms 단위로 모아서
  }
}
```

지난 말풍선은 `memo`로 격리했습니다. 내용이 같으면 다시 그리지 않아서, 새 답변이 흐르는 동안 이전 대화가 같이 파싱되지 않아요.

### 하다가 만난 버그 하나

코얼레싱을 넣고 나서 **사용자 질문 말풍선이 답변으로 덮어써지는** 버그가 생겼습니다. `paint()` 안에서 "이번 답변 말풍선을 이미 붙였나"를 바깥 변수(`hasBubble`)로 판단했는데, `setMessages`에 넘긴 updater는 즉시 실행되지 않고 **다음 렌더에서** 돌아요. 그 사이에 `hasBubble = true`가 먼저 지나가 버려서, 첫 그리기조차 "마지막 말풍선을 교체" 분기를 탔고, 그 마지막 말풍선이 사용자 질문이었던 거예요.

고친 방법은 바깥 변수 대신 배열 자신에게 묻는 것이었습니다. 답변 말풍선은 id가 이번 실행 id라서, 마지막 항목의 id가 같으면 갱신하고 아니면 새로 붙입니다. 타이밍과 무관해져요.

```ts
setMessages(m => {
  const next = m.slice();
  const last = next[next.length - 1];
  if (last?.id === runId) next[next.length - 1] = bubble;
  else next.push(bubble);
  return next;
});
```

### 얼마나 줄었나, 그리고 언제 효과가 없나

랩의 가짜 스트림(조각 약 95개, 중간에 1.6초 도구 호출 대기)으로 세어 봤습니다.

| 조각 속도    | 조각마다 렌더 | 50ms 코얼레싱 |
| ------------ | ------------- | ------------- |
| 초당 120조각 | 96회          | 16회          |
| 초당 40조각  | 96회          | 34회          |
| 초당 10조각  | 96회          | 97회          |

초당 10조각에서는 오히려 한 번 더 그렸어요. 조각 간격(100ms)이 50ms보다 길면 모을 조각이 없어서, 코얼레싱은 렌더 횟수를 줄이지 못하고 확정 시점 렌더만 더해집니다. **코얼레싱은 조각이 50ms보다 촘촘하게 올 때만 효과가 있어요.** 실제 모델 응답은 대부분 이보다 빠르게 오지만, 느린 모델이나 느린 네트워크에서는 이 기법이 하는 일이 없다는 걸 알고 쓰는 게 맞습니다.

50ms라는 값은 "사람 눈에 끊겨 보이지 않을 만큼 짧고, 조각 여러 개를 묶을 만큼 긴 값"으로 잡았습니다. 여러 값을 비교해서 고른 건 아니에요.

## 2. 새로 도착한 글자만 페이드인

### 왜 CSS만으로는 안 되나

조각이 툭툭 붙으면 딱딱해 보여서, 처음엔 말풍선에 페이드 애니메이션을 걸었습니다. 그러면 조각이 올 때마다 **말풍선 전체가** 다시 흐려졌다가 선명해져요. 이미 읽고 있던 문장까지 같이 깜빡입니다. 랩 왼쪽 말풍선이 정확히 이 모습이에요.

새 글자만 떠오르게 하려면 글자마다 자기 등장 시각을 가져야 하고, 그러려면 글자마다 요소가 있어야 합니다.

### 고친 방법 — 글자 번호마다 지연을 한 번만 정한다

마크다운을 HTML 트리로 바꾼 뒤(rehype 단계), 텍스트 노드를 글자 단위 `<span>`으로 쪼갭니다. 핵심은 **글자 번호마다 등장 지연을 딱 한 번만 정해서 장부에 적어 두는 것**이에요.

```ts
const STEP_MS = 14; // 왼쪽에서 오른쪽으로 번진다고 느끼는 간격
const MAX_DELAY_MS = 360; // 한꺼번에 많이 와도 꼬리가 늘어지지 않게

export function rehypeReveal(state: { delays: number[] }) {
  return () => (tree: Root) => {
    let idx = 0;
    let base = -1; // 이번 렌더에서 처음 보는 글자의 시작 번호

    const tokenize = (value: string) =>
      Array.from(value).map(ch => {
        const i = idx++;
        if (state.delays[i] === undefined) {
          if (base < 0) base = i;
          state.delays[i] = Math.min((i - base) * STEP_MS, MAX_DELAY_MS);
        }
        return span("rv-tok", `animation-delay:${state.delays[i]}ms`, ch);
      });

    walk(tree, tokenize);
  };
}
```

스트리밍은 텍스트가 **뒤에 붙기만** 합니다. 그래서 글자 번호(문서 순서)는 변하지 않아요. 이미 뜬 글자는 다음 렌더에서도 같은 번호, 같은 지연으로 나오고, props가 같으니 React가 그 DOM을 건드리지 않습니다. 진행 중이던 CSS 애니메이션도 끊기지 않아요. 새 번호만 새 DOM이 되어 그때 애니메이션이 재생됩니다.

장부는 말풍선마다 `useRef`로 들고 있습니다. 렌더마다 새로 만들면 모든 글자가 "처음 보는 글자"가 되어 전부 다시 깜빡여요.

```css
.rv-tok {
  animation: rv-in 700ms cubic-bezier(0.22, 1, 0.36, 1) backwards;
}
@keyframes rv-in {
  from {
    opacity: 0;
  }
  to {
    opacity: 1;
  }
}
@media (prefers-reduced-motion: reduce) {
  .rv-tok {
    animation: none;
  }
}
```

- **opacity만 움직입니다.** inline 요소에는 transform이 안 먹고, filter는 글자 수천 개에 걸면 합성 비용이 커요.
- **fill-mode는 `backwards`입니다.** 시작 전에는 투명 상태를 채워 "번쩍 보였다 사라지는" 걸 막고, 끝나면 규칙에서 손을 떼 요소를 붙들지 않아요.
- **스트리밍 중인 마지막 답변에만 켭니다.** 다 쓴 답변까지 글자 단위 span으로 남겨 둘 이유가 없어요.

### 한계

- **마크다운 구조가 늦게 완성되면 그 문단이 한 번 다시 떠요.** `**bo`까지 왔을 때는 그냥 텍스트였다가, `**bold**`가 완성되는 순간 트리 모양이 바뀌어 그 구간 번호가 밀리기 때문이에요. 보기에 자연스러워서 그대로 뒀습니다.
- **표와 목록 뼈대 안의 텍스트는 쪼개면 안 됩니다.** 마크다운 표를 HTML 트리로 바꾸면 `<table>`·`<tr>` 사이사이에 줄바꿈만 든 텍스트 노드가 끼어 있어요. 그걸 `<span>`으로 감싸면 `<table>`의 직계 자식에 `<span>`이 생기고, React가 hydration 오류를 냅니다. 실제로 이 오류를 한 번 냈고, `table`·`tr`·`ul` 같은 태그 안의 텍스트는 건드리지 않게 고쳤어요.
- **코드 블록도 쪼개지 않습니다.** 등폭 정렬이 깨지고 span 수가 폭증해요.

## 3. 닫히지 않은 블록은 렌더러에 넘기지 않는다

### 문제

답변 안의 차트는 이런 블록으로 옵니다.

````md
```chart
{"title":"지역별 충전기 수","data":[["서울",412],["경기",356]]}
```
````

스트리밍 중에는 JSON이 반만 와 있어요. 이걸 차트 렌더러에 넘기면 파싱이 실패하고, 실패 화면이 보였다가 마지막 조각이 오는 순간 차트로 바뀝니다. 랩에서 세 보면 이 짧은 스트림에서도 **실패 화면이 33번 렌더**됐어요.

### 고친 방법

블록을 잘라내는 정규식이 **닫는 ` ``` `가 왔는지**를 구분하게 했습니다.

````ts
// 닫는 ``` 가 없어도 문자열 끝까지 블록으로 잡는다.
// m[3] 이 "```" 면 닫힌 블록이다.
export const BLOCK_RE =
  /```(chart|choices|mermaid|approval|map)[^\n]*\r?\n([\s\S]*?)(```|$)/g;
````

- 닫히지 않았으면 렌더러 대신 **"차트 그리는 중…" 자리표시자**를 그립니다. 끝을 모르는 대기라서 글자 위로 빛이 지나가게(shimmer) 했어요.
- 끝이 `(```|$)`인 게 중요합니다. 닫는 기호가 없을 때 문자열 끝까지 블록으로 잡지 않으면, 블록 전체가 일반 마크다운 코드 블록으로 흘러가 버려요. 그러면 실패 화면 대신 JSON 원문이 보였다가 사라집니다.
- **선택지 버튼은 완성 전에는 아예 그리지 않습니다.** 차트는 자리표시자로 충분하지만, 선택지가 반만 뜨면 사용자가 잘못 누를 수 있어요.
- 지도와 다이어그램은 블록이 처음 나올 때 컴포넌트를 불러옵니다(dynamic import). 불러오는 동안에도 같은 자리표시자를 써서 화면 높이가 출렁이지 않게 했어요.

## 4. 멈춘 구간을 보여준다 — 점 세 개

### 문제

첫 글자가 오기 전에는 "생각 중…"을 보여줬어요. 그런데 모델이 문장을 쓰다가 도구를 부르면, 델타가 한동안 끊깁니다. 그동안 말풍선은 글자가 멈춘 채 **다 쓴 것처럼** 보여요. 실제로는 종료 신호를 기다리는 중인데요. 이 구간에 "아직 진행 중"이라고 말해 줄 수단이 없었습니다.

### 고친 방법

스트림이 열려 있는 동안 말풍선 아래에 점 세 개(`.` → `..` → `...`)를 둡니다.

- **점 세 개는 늘 자리를 차지하고, 투명도만 바꿉니다.** 글자를 실제로 넣고 빼면 폭이 1/3씩 출렁여서, 바로 앞 문장의 마지막 줄까지 같이 흔들려요.
- **문장 뒤가 아니라 아래 줄에 둡니다.** 답변이 마침표로 끝나는 일이 흔해서, 이어 붙이면 "끝났습니다...."처럼 문장부호와 구별되지 않아요.
- **둘째·셋째 점에 keyframe을 따로 줬습니다.** 하나의 keyframe에 delay만 달리하면 주기가 되감길 때 `..` `.` `...`처럼 순서가 무너져요.
- 스크린리더에는 `role="status"`와 "응답을 기다리는 중"이 한 번만 읽히고, 점 자체는 `aria-hidden`입니다. 모션을 줄이는 설정에서는 점 세 개를 그냥 켜 둬요. 표시 자체가 사라지면 "기다리는 중"이라는 사실을 전할 수단이 없어지니까요.

같은 이유로, 스트리밍 중에는 답변 복사 버튼을 숨깁니다. 반만 쓴 답을 복사해 가면 그게 전부인 줄 알 테니까요. 버튼이 나타나는 것 자체가 "다 썼다"는 표시도 됩니다.

## 정리 — 네 가지를 다 켜면 되나

| 기법                        | 해결하는 것                 | 효과가 없는 때                                          |
| --------------------------- | --------------------------- | ------------------------------------------------------- |
| 50ms 코얼레싱               | 조각마다 반복되는 렌더·파싱 | 조각이 50ms보다 느리게 올 때                            |
| 새 글자만 페이드인          | 말풍선 전체 깜빡임          | 마크다운 구조가 늦게 완성될 때(그 문단만 한 번 다시 뜸) |
| 닫히지 않은 블록 자리표시자 | 반쪽 JSON 실패 화면         | 블록 형식 자체가 틀렸을 때(닫혀도 실패)                 |
| 멈춘 구간 점 세 개          | 다 쓴 것처럼 보이는 멈춤    | —                                                       |

대부분의 경우 넷 다 켜 두는 게 맞았습니다. 다만 코얼레싱은 조각 속도에 따라 아무 일도 안 할 수 있고, 페이드인에는 받아들이기로 한 한계가 있어요. 그리고 이 글의 숫자는 **실제 사용자 측정이 아니라 랩의 가짜 스트림에서 센 값**입니다. 실제 화면에서 체감이 나아졌다는 건 팀 안에서 같이 써 본 판단이에요.

## 마무리

LLM 답변은 "다 오면 그린다"가 아니라 "오는 동안 계속 그린다"는 점에서 일반 API 응답과 다릅니다. 그래서 렌더를 언제 할지(코얼레싱), 무엇을 다시 그릴지(글자 단위 장부), 무엇을 아직 그리지 않을지(닫히지 않은 블록), 멈춤을 어떻게 보여줄지(점 세 개)를 따로 정해야 했어요.

돌아보면 네 가지 모두 같은 질문이었습니다. **"이 조각이 왔을 때, 사용자가 이미 본 것은 그대로 두고 있는가?"** 이미 읽은 문장이 다시 깜빡이거나, 이미 본 내용이 실패 화면으로 바뀌거나, 끝난 줄 알았던 답이 이어지면, 사용자는 화면을 믿지 않게 됩니다.
