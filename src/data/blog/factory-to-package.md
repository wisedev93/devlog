[팩토리 글](/posts/factory-in-react)을 발행하고 나서, 팩토리를 npm 패키지로 꺼내기로 했습니다. 이름도 정했어요. Zod + React Query + CRUD의 앞 글자를 따서 `zqc-kit`. npm에서 이름이 비어 있는 것까지 확인했으니 이제 코드를 옮기기만 하면 되는 상황이었습니다.

옮기기 전에 질문 하나에서 막혔습니다. **이걸 남이 설치할 이유가 있나?** 회사 코드에서는 분명히 효과가 있었습니다. 페이지당 144줄이 59줄이 됐고, 누가 작성하든 같은 모양의 코드가 나왔어요. 그런데 그건 직접 만든 팩토리를 "우리팀에 적용한" 효과고, npm에 올린다는 건 다른 팀이나 개발자가 자기 프로젝트에 넣을 만한 이유가 있어야 해요.

그래서 이유를 찾으려고 다양한 방법으로 실험해봤습니다. 실험의 중심 질문은 하나였어요. **API 문서를 주면 AI는 얼마나 정확하게 코드로 옮기는가, 그리고 팩토리는 정확도를 올리는가.** 결론부터 말하면 AI는 팩토리 없이도 정확했고, 저는 패키지를 배포하지 않기로 했습니다.

## Table of contents

## 첫 번째 가설 — CRUD 팩토리를 범용화하면 된다

처음 계획은 단순했습니다. 기존 팩토리에서 사내 프로젝트에만 맞는 부분을 걷어내면 범용 라이브러리가 된다는 것. 걷어낼 것도 분명했어요.

| 기존 팩토리                   | 범용으로 바꿀 것                             |
| ----------------------------- | -------------------------------------------- |
| axios 인스턴스를 직접 import  | 인자로 주입                                  |
| `response.data.data` 고정     | 응답 봉투를 벗기는 함수(`unwrap`)를 설정으로 |
| 스키마 네 개 모두 필수        | 필요한 것만                                  |
| 무효화 키를 문자열로 조합     | 계층형 배열 키                               |
| 엑셀 내보내기, 빈 목록 토스트 | 회사 요구라 제외                             |

코드를 그대로 꺼내지 않고 이 표대로 처음부터 다시 작성했고, 테스트와 zod 3·4 호환 확인까지 마쳤습니다. 그리고 README에 "왜 이 라이브러리인가"를 쓰려고 대안이 못하는 것을 조사하다가 첫 가설이 깨졌어요.

- OpenAPI 명세가 있는 팀은 orval이나 Hey API 같은 코드 생성기가 클라이언트, React Query 훅, Zod 스키마까지 만들어 줍니다. 이런 팀에게 손으로 스키마를 쓰는 팩토리는 오히려 후퇴예요.
- 풀스택 TypeScript 팀은 tRPC나 ts-rest로 타입을 서버와 공유하니 필요가 없습니다.
- 쿼리 키와 훅 부분만 보면 이미 query-key-factory, react-query-kit 같은 라이브러리가 있습니다.

CRUD라는 모양 자체의 한계는 팩토리 글에서 이미 측정했습니다. 팩토리를 쓰는 페이지 다섯, 안 쓰는 페이지 셋. 우리 팀에서도 다 커버하지 못하는데 남에게 권할 수는 없었습니다. **CRUD 팩토리는 이미 해결된 문제의 재구현이었습니다.**

## 두 번째 가설 — AI가 문서를 더 정확하게 옮기게 하는 도구

범위를 다시 잡으면서 [코드베이스 하네스 글](/posts/codebase-is-harness)의 결론을 떠올렸습니다. 페이지 단위 위임은 AI가 더 적게 결정하게 해서 성립했다는 것. 백엔드가 OpenAPI 명세를 주지 않는 팀도 분명히 존재하고, 그런 팀에서는 AI가 노션 표나 DTO 코드를 보고 API 연결 코드를 짭니다. 그때 AI가 결정할 것을 좁혀서 더 정확한 코드를 쓰게 하는 도구라면, 누군가 설치할 이유가 될 수 있을 것 같았어요.

그래서 실험용으로 두 가지를 만들었습니다. 하나는 엔드포인트 하나에 선언 하나를 쓰는 라이브러리입니다. 무효화도 mutation마다 선언하게 해서, AI가 쓰는 건 스키마와 선언 몇 줄뿐이고 요청·캐시·검증 동작은 라이브러리가 맡아요.

```ts title="users.contract.ts"
export const getUser = defineQuery({
  key: ["users", "detail"],
  path: "/users/:id", // { id } 타입이 경로 문자열에서 추론된다
  response: User,
});

export const updateUser = defineMutation({
  method: "PATCH",
  path: "/users/:id",
  body: UpdateUserBody,
  response: User,
  invalidates: ({ id }) => [getUsers, getUser.key({ id })],
});

// 컴포넌트
useQuery(getUser.options({ id }));
useMutation(updateUser.options()).mutate({ id, body: { name } });
```

다른 하나는 AI가 쓴 스키마를 기계로 확인하는 검증 명령입니다. 모든 응답 스키마를 저장해 둔 샘플 응답이나 개발 서버의 실제 응답에 대고 돌리고, 어긋나면 어느 필드에서 무슨 값을 받았는지 출력해요.

```
✗ getNotices  GET /notices  src/api/notices.contract.ts
    ✗ [bad] __zqc__/fixtures/getNotices.bad.json
        items[0].pinned: Invalid option: expected one of "Y"|"N" (received true)
    ! [default] not in schema (stripped): items[].views
```

여기에 "문서를 보고 명세 파일과 샘플 응답을 만든 뒤, 검증이 통과할 때까지 고쳐라"라는 스킬 문서를 붙였습니다. 이게 정말 AI가 더 정확한 코드를 쓰게 만드는지는 재 봐야 알 수 있었습니다.

## 측정 설계

실제 관리자 API는 공개할 수 없으니 가짜 API 문서 10개를 만들었습니다. 각 문서는 프론트엔드 개발자가 실제로 받는 형식을 하나씩 따랐어요.

| 케이스   | 형식                                     | 응답 봉투                   |
| -------- | ---------------------------------------- | --------------------------- |
| 공지     | 노션 표                                  | `{ success, data }`         |
| 쿠폰     | Spring 컨트롤러 + DTO 코드               | 없음                        |
| 회원     | Postman 컬렉션(저장된 예시 응답)         | `{ code, message, result }` |
| 주문     | 슬랙 스레드에 붙인 샘플 JSON             | 없음                        |
| 상품     | 엑셀 명세를 CSV로 내보낸 것              | `{ success, data }`         |
| 1:1 문의 | 백엔드 개발자의 메일(설명과 예시가 다름) | `{ success, data }`         |
| 배너     | 영문 마크다운                            | 없음                        |
| 정산     | Kotlin data class + 전역 `NON_NULL`      | `{ data }`                  |
| 예약     | 부록 코드표가 있는 정의서                | `{ success, data }`         |
| 직원     | NestJS DTO, 예시 응답 없음               | 없음                        |

문서마다 실무에서 실제로 겪는 함정을 넣었습니다. 엔드포인트는 모두 43개, 그중 무효화 대상이 정해진 mutation이 20개입니다.

| 함정                                        | 문서를 제대로 읽었다면                        |
| ------------------------------------------- | --------------------------------------------- |
| 설명은 "숫자"라는데 예시 JSON의 ID는 문자열 | 예시를 따라 `z.string()`                      |
| 표에는 없고 예시에만 있는 필드              | 예시를 따라 필드 추가                         |
| 예시에 `null`이 보이는 필드                 | `.nullable()`                                 |
| "환불 안 된 주문은 refund 키 자체가 없어요" | `.optional()`                                 |
| Kotlin 전역 `NON_NULL` 설정                 | null 가능 필드를 `.optional()`로              |
| Prisma `Decimal`은 문자열로 직렬화          | `z.string()`                                  |
| 상태 코드가 문서 끝 부록에만 있음           | 부록을 찾아 `z.enum`                          |
| 상품 수가 바뀌는 카테고리 목록              | 상품 등록·수정·삭제 시 카테고리 목록도 무효화 |

채점은 생성기가 보지 못하는 정답 응답 56개로 했습니다. 생성된 응답 스키마를 이 응답들에 대고 돌려서 통과하는지, 스키마가 검증하지 못한 필드는 없는지, mutation이 갱신해야 할 쿼리를 정확히 무효화하는지를 셉니다.

조건은 세 가지입니다.

- **A. 자유 생성**: "Zod로 검증하고 TanStack Query 훅을 만들라"는 팀 컨벤션 수준의 지시만 준다
- **B. 라이브러리 + 스킬 + 검증 명령**
- **C. 라이브러리 + 스킬, 검증 없음**: B와 비교해서 검증 명령만의 효과를 분리한다

생성은 Claude Code의 서브에이전트(Claude Sonnet)가 했고, 에이전트 하나가 한 조건의 케이스 5개를 맡았습니다. 실험 전에 두 가지를 확인했어요. 제가 직접 쓴 정답 코드가 모든 지표에서 100%가 나오는지(채점기와 정답 데이터가 서로 맞는지), 그리고 정답 코드에서 `.nullable()` 하나를 지우면 점수가 실제로 떨어지는지(5개 중 2개로 떨어졌습니다). 생성기가 도는 동안 정답 파일은 접근할 수 없는 곳으로 옮겨 뒀고요.

## 1차 — 문서가 맞을 때

| 조건                 | 정답 응답 통과 | 무효화 정확도       | 케이스당 작성 코드 |
| -------------------- | -------------- | ------------------- | ------------------ |
| A. 자유 생성         | 56/56          | 20/20 (직접 읽어서) | 135줄              |
| B. 라이브러리 + 검증 | 56/56          | 20/20 (스크립트로)  | 59줄               |
| C. 라이브러리만      | 56/56          | 20/20 (스크립트로)  | 59줄               |

세 조건 모두 100%였습니다. 채점기가 고장 난 건 아닌지 다시 확인했는데, 생성된 코드에 `z.any()` 같은 느슨한 스키마는 하나도 없었고 위의 음성 대조도 정상이었어요. 위 표의 함정을 세 조건이 전부 혼자 풀었습니다. 설명과 예시가 다르면 예시를 따랐고, 그 결정을 보고서에 따로 적었어요. `NON_NULL` 설정 한 줄을 보고 null 가능 필드를 `.optional()`로 바꿨고, 부록의 코드표를 찾아 enum으로 만들었습니다. 무효화도 마찬가지였어요. "상품 수가 바뀐다"는 문서의 한마디를 보고 상품 mutation에 카테고리 목록 무효화를 넣었고, 자유 생성 조건의 20개 mutation도 제가 하나씩 읽어 보니 빠진 곳이 없었습니다.

**두 번째 가설은 여기서 깨졌습니다.** 이 문서들에서는 라이브러리도 검증 명령도 정확도를 올릴 여지가 없었어요. B와 C가 같으니 검증 단계가 더한 효과도 측정되지 않았습니다. 덧붙여 B가 저장할 수 있었던 샘플은 43개 엔드포인트 중 14개분뿐이었습니다. 문서에 예시가 없으면 샘플도 없고, 스킬은 샘플을 지어내지 말라고 했으니까요.

## 2차 — 문서가 틀렸을 때

1차가 잰 건 "AI가 문서를 잘못 읽는가"였습니다. 하지만 실무에서 API 연결이 깨지는 더 흔한 이유는 문서 자체가 틀린 경우예요. 문서를 아무리 꼼꼼히 읽어도 알 수 없는 어긋남이죠. 그래서 문서는 그대로 두고, 서버의 실제 응답만 문서와 다르게 바꿨습니다. 문서에 없는 enum 값, 문서는 값이 있다는데 null로 오는 필드, 숫자인데 문자열로 오는 값, 꺼져 있던 `NON_NULL` 같은 것들이요. 케이스마다 두 개씩, 모두 20개입니다. 그리고 실제 응답을 돌려주는 읽기 전용 개발 서버를 케이스마다 띄우고, 세 조건 모두의 과제에 "개발 서버가 여기 있다"고 알려줬습니다.

대조군부터 확인했습니다. 1차의 정답 코드, 즉 문서를 완벽하게 읽은 코드는 2차의 정답 응답을 **30/56(54%)** 만 통과했어요. 문서만 읽어서는 이 이상 올라갈 수 없다는 뜻이고, 이번에는 검증 명령이 차이를 만들 여지가 충분했습니다.

| 조건                      | 정답 응답 통과 | 케이스당 작성 코드 |
| ------------------------- | -------------- | ------------------ |
| 문서를 완벽하게 읽은 코드 | 30/56          | —                  |
| A. 자유 생성              | 56/56          | 121줄              |
| B. 라이브러리 + 검증      | 56/56          | 59줄               |
| C. 라이브러리만           | 56/56          | 59줄               |

또 세 조건 모두 100%였습니다. 기록을 보니 A와 C의 에이전트도 스스로 개발 서버를 호출해서 응답을 확인하고, 문서보다 서버를 따른 뒤 어긋난 부분을 보고서에 정리했어요. 어떤 에이전트는 "개발 서버의 상세 조회가 요청한 ID와 다른 데이터를 돌려준다"처럼, 제가 실험을 단순하게 만들려고 넣은 가짜 서버의 한계까지 찾아서 보고했습니다. 과제에 개발 서버가 있다고 적혀 있으면, 모델은 도구가 없어도 직접 확인했습니다.

차이가 난 건 스키마를 얼마나 엄격하게 썼느냐였어요. A는 enum 12개 중 1개(예약 상태)를 `z.string()`으로 풀었고, `"4"`를 조용히 `4`로 바꾸는 `z.coerce.number()`를 4곳에 썼습니다. B와 C는 12개를 모두 enum으로 유지하고 새 값을 추가했어요. 차이는 있지만 정확도를 가를 만큼은 아니었습니다.

## 3차 — 코드를 다 쓴 뒤에 서버가 바뀔 때

생성 시점의 정확도로는 차이를 찾지 못했으니, 생성이 끝난 뒤를 봤습니다. 실무에서 API 연결 코드가 깨지는 건 대부분 이 시점이에요. 코드를 쓸 때는 맞았는데, 몇 주 뒤 백엔드에서 필드 이름을 바꾸거나 상태 값을 하나 추가합니다.

2차에서 생성된 코드는 그대로 두고, 케이스마다 서버 응답을 하나씩 더 바꿨습니다(필드 이름 변경, 새 enum 값, 숫자가 문자열로, 필드가 null 가능으로 등). 그리고 B 프로젝트에서 검증 명령을 개발 서버에 대고 실행했더니 10건을 모두 잡았고, 바뀌지 않은 엔드포인트를 실패로 잘못 잡은 경우는 없었어요. 출력에는 `orders[0].totalAmount: received "10000"`처럼 엔드포인트, 필드, 받은 값이 그대로 나왔습니다.

솔직하게 말해서 이 측정을 처음 돌렸을 때도 10건이 전부 "잡음"으로 나왔는데, 자세히 보니 실패 이유가 전부 연결 오류였습니다. 측정 스크립트가 검증 명령을 동기로 실행하면서, 같은 프로세스에 띄운 가짜 서버가 응답을 못 하고 있었던 거예요. 비동기 실행으로 고쳐서 다시 돌렸고, 위 결과는 필드 단위로 확인한 두 번째 결과입니다. 결과가 기대와 딱 맞으면 오히려 한 번 더 열어 봐야 한다는 걸 다시 배웠습니다.

같은 변경이 각 조건의 코드에 런타임에서 주는 영향도 쟀습니다. 정답 응답 통과가 A는 47/56, B와 C는 45/56이었어요. A가 덜 깨진 이유는 공지 케이스 하나인데, A가 `viewCount`를 선택 필드로 느슨(optional)하게 써 둔 덕분에 이름이 `views`로 바뀌어도 검증을 통과했습니다. 에러가 나지 않으니 화면에서 조회수가 조용히 사라질 뿐이고요. 느슨한 스키마는 덜 깨지는 게 아니라, 깨진 걸 늦게 알게 될 뿐입니다.

여러 case 중 라이브러리 쪽이 분명히 앞선 건 이것 하나였습니다. 그런데 이 효과를 얻는 데 npm 패키지가 필요한지는 따로 생각해 봐야 했어요.

## 차이는 정확도가 아니라 절차였다

배포 여부를 정하기 전에 하나를 더 확인했습니다. 팩토리 글에서 말한 "누가 작성하든 같은 코드가 나온다"는 효과요. 정확도가 같다면, AI가 쓴 코드는 원래부터 일관된 건 아닐까요. 두 번의 실험에서 나온 자유 생성 결과물 20개를 분석했습니다. 같은 모델에게 같은 지시를 준 결과입니다.

구조는 이미 일관됐습니다.

| 항목                                | 20개 중 |
| ----------------------------------- | ------- |
| `queryOptions` 헬퍼 사용            | 20      |
| `lists()`/`detail()` 쿼리 키 팩토리 | 19      |
| 응답을 `.parse`로 검증              | 20      |

요즘 모델은 TanStack Query 커뮤니티에서 권하는 모양으로 수렴해서, 구조는 알아서 비슷하게 씁니다. 팩토리 글에서 다룬 `useItemList`와 `useGetPlanPrices` 같은 이름 불일치는 이번 결과물에서 거의 보이지 않았어요.

차이나는 건 동작을 정하는 결정이었습니다.

- 수정·삭제 뒤 상세 캐시를 다루는 방식이 네 가지로 나뉘었습니다. 응답으로 캐시를 직접 덮는 것(8개), 거기에 삭제 시 캐시 제거를 더한 것(4개), 캐시를 덮고 무효화도 하는 것(4개), 무효화만 하는 것(2개). 상세 화면이 없는 배너 케이스 2개는 제외했습니다.
- 무효화를 거는 위치도 `onSuccess`만 쓴 것이 5개, `onSettled`만 쓴 것이 3개, 두 가지를 섞은 것이 12개였어요. `onSettled`는 요청이 실패해도 다시 불러오니까 실제 동작이 다릅니다.
- 4개는 `z.coerce`로 타입이 어긋난 걸 숨겼습니다.

넷 다 틀린 코드는 아닙니다. 그래서 정확도 채점에서는 드러나지 않았어요. 다만 같은 저장소에 이 네 가지가 섞여 있으면, "이 화면은 저장 후 왜 목록이 바로 안 바뀌지?"를 화면마다 따로 확인해야 합니다. 팩토리 글에서 코드를 명세와 절차로 나눴는데, AI가 쓴 코드에서 차이나는 건 정확히 절차였어요. 모양은 모델이 이미 맞추고, 절차는 파일마다 새로 결정합니다.

## 그래서 배포하지 않기로 했다

세 번의 실험을 거치고 남은 효과는 세 가지였습니다.

1. AI가 파일마다 새로 내리던 절차 결정을 한 곳으로 모은다
2. 작성할 코드가 케이스당 121~135줄에서 59줄로 줄어든다
3. 코드를 다 쓴 뒤 서버가 바뀌면, 사용자보다 먼저 안다

셋 다 실제 효과입니다. 그런데 셋 다 npm 패키지 없이 얻을 수 있어요.

1과 2는 사내 프로젝트가 이미 하고 있는 일입니다. 저장소 안의 팩토리 두 개와 `CLAUDE.md`, 스킬 문서가 절차를 한 곳에 모으고, 페이지마다 쓸 코드를 줄여 줍니다. 팩토리가 프로젝트의 요구에 맞춰 바뀔 수 있다는 점에서는 오히려 저장소 안에 있는 편이 낫고요. [팩토리 글](/posts/factory-in-react)에서 엑셀 내보내기가 공통 요구가 됐을 때 팩토리에 바로 추가했던 것처럼요.

3도 마찬가지입니다. 회사 코드는 모든 응답을 `validateResponse`로 검증하고, 어긋나면 엔드포인트와 필드를 Sentry로 보냅니다. 서버가 바뀌면 사용자보다 늦게라도 알게 되는 구조는 이미 있어요. 그걸 배포 전에 알고 싶다면 개발 서버에 대고 스키마를 돌리는 CI 스크립트 하나를 저장소에 두면 됩니다. 실험에서 만든 검증 명령의 핵심도 설정 파일을 읽고, 명세를 찾고, 응답을 받아 `safeParse`를 돌리는 수십 줄이었어요.

결국 npm 패키지가 더해 주는 건 "누군가 설치할 수 있다"는 것 하나인데, 처음 질문으로 돌아가면 다른 누군가가 설치할 이유를 찾지 못했습니다. OpenAPI 명세가 있는 팀에게는 코드 생성기가 있고, 없는 팀에게는 AI가 문서를 이미 정확하게 옮겨 줍니다. 남은 건 절차를 모으는 일인데, 그건 팀마다 절차가 달라서 각자 저장소 안에서 하는 편이 맞다고 판단했어요.

## 한계

- 모델 하나(Claude Sonnet)로, 조건×케이스마다 한 번씩만 돌렸습니다. 실행마다 결과가 얼마나 달라지는지는 재지 않았어요.
- 가짜 문서 10개는 제가 함정을 넣어 만든 것이라, 실제 문서보다 정돈돼 있습니다. 수백 개 엔드포인트가 한 문서에 섞여 있거나, 같은 필드를 문서 곳곳에서 다르게 설명하는 경우는 시험하지 않았습니다.
- 2차 실험에서 모든 조건에 개발 서버가 있다고 알려줬습니다. 개발 서버의 존재를 모르는 경우는 시험하지 않았습니다.
- 가짜 개발 서버는 엔드포인트마다 응답 하나만 돌려주고 ID와 필터를 무시합니다.
- 라이브러리, 스킬 문서, 실험 케이스, 채점기를 모두 같은 사람이 만들었습니다. 정답 코드로 채점기를 확인하고 음성 대조를 둔 것도 이 편향을 줄이려는 장치였지만, 완전히 없앨 수는 없습니다.
- 1차와 2차 사이에 스킬 문서에 개발 서버 사용법을 추가했습니다. 1차 결과를 보고 바꾼 것이고, A 조건의 지시는 바꾸지 않았습니다.

## 마무리

CRUD 팩토리를 npm 패키지로 꺼내려다, 올리기 전에 남이 설치할 이유부터 재 봤습니다. 범용 CRUD 팩토리는 이미 해결된 문제였고, "AI가 문서를 더 정확하게 옮기게 하는 도구"라는 두 번째 가설은 실험 두 번에서 연달아 깨졌어요. 문서가 맞을 때 AI는 숨긴 정답 응답 56개를 모두 통과했고, 문서가 틀렸을 때는 개발 서버를 직접 호출해서 바로잡았습니다. 남은 효과는 절차 결정을 한 곳에 모으는 것과 서버 변경을 미리 아는 것이었는데, 둘 다 저장소 안의 코드로 이미 얻고 있거나 쉽게 얻을 수 있는 것이라 배포하지 않기로 했습니다.

[코드베이스 하네스 글](/posts/codebase-is-harness)에서는 AI에게 얼마나 맡길 수 있는지는 모델이 아니라 코드베이스가 정한다고 썼습니다. 이번 실험은 그 결론의 범위를 좁혀 줬어요. 문서를 읽고 스키마를 정확하게 쓰는 일은 이제 모델이 해냅니다. 코드베이스가 정해야 하는 건 모델이 파일마다 다르게 내리는 절차 결정과, 코드를 다 쓴 뒤에도 계속 확인해야 하는 것들입니다. 그리고 그건 팀마다 다르기 때문에, 패키지가 아니라 각자의 저장소 안에 있어야 한다고 생각합니다.
